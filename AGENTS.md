# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.
- `CONTRACT.md` and everything under `contract/` are the ratified answer key. `contract/*.test.ts` files ARE allowed to change, but narrowly: they import the real implementation and assert on it, so an authorized issue can add or repoint a test's *import*, or add a genuinely new ratified assertion the Client explicitly asked for — what must never happen is production logic living in `contract/surface.ts`, which stays purely declarative (types only, no functions). Never touch `CONTRACT.md` itself, and never change or remove an existing assertion without an explicit ruling — the one standing exception is rule 9's own text, rewritten to describe CI-side blocking instead of discarding under an explicit Client ruling, confirmed a second time when flagged again (PR #54 follow-ups); an edit to CONTRACT.md is still never yours to make on your own initiative, only under a ruling exactly like that one. `createForeman` (issue #7) now wires `src/record` + `src/line` + `src/brain` + `src/config` together in `src/foreman/`, so most contract rules are green. `foreman.verdict` (issue #10, rule 6) is implemented in `src/foreman/verdict.ts`: `accept`/`wrong` close the task; `fix` re-enters the same warm worker on the same line (`src/line/resume.ts`'s `reopenProductionLine`, checked out at the identical worktree path a Brain's session was born in) with the Client's note as a correction. A `fix` draws from no attempt budget (issue #65, Client ruling 2026-08-07: "separate the two, unlimited but counted") — `do()`'s own retry loop still obeys rule 3's counted budget exactly as before, but a `fix` the Client asks for has no ceiling and never refuses, since he is the stop condition, not the machine (the `attempts-exhausted` error code was deleted from `errors.ts` with that refusal — it had no other thrower, and `do()` exhausting its own budget delivers an honest `failure-report` per rule 2 rather than throwing; do not reintroduce it). Each round is counted and reported instead — `queries.ts`'s `fixRoundOf` derives the count from `"verdict-recorded"` events rather than storing it — see `src/foreman/README.md`. Only rule 10's cap-refusal test (issue #11) is still legitimately red — `npm test` failing on exactly that is expected, not a bug; any other red contract test is a real regression.
- `npm test` first runs `tsc --noEmit` (over `contract/`, `src/` **and** `skill/` - a harness's own TypeScript under `skill/` is typechecked like everything else), then runs every `*.test.ts` under `contract/` (the answer key - see the rules above) and `src/`, at any depth - discovery is a `find`, not a shell glob, so a nested test file is never silently skipped. When adding a feature, colocate its test next to the source file it covers (`foo.ts` + `foo.test.ts`), matching how `contract/` colocates one test file per rule.
- Module layout under `src/<feature>/`: `errors.ts` (a typed error class with a `code` for branching, message written to be shown to the Client verbatim), one file per behavior (e.g. `load.ts`, `registry.ts`), an `index.ts` barrel, and a `helpers/` subfolder for test-only fixtures. A `types.ts` holds internal shapes only where a module has any; a type that also appears in `contract/surface.ts` (the seam the module is implementing) is declared there once and imported into `src/` with `import type` (issue #45) — never redeclared. The test: if changing the type changes what Fabrica *promises* the Client, it's a contract type; if it only changes how code is organised, it stays in `src`. See `src/config/` as the reference example for a module with real internal types, and `src/brain/`, `src/foreman/`, `src/line/` for modules that now hold no shared-with-the-contract types of their own, only re-exports or `import type` from the contract (genuinely internal shapes like `src/line/safety.ts`'s `WorktreeEntry` stay put).
- The record home (`~/.fabrica` by default) is never hardcoded past the outermost CLI layer — every function that touches it takes `recordHome: string` as an explicit parameter, so parallel workers/tests never share state. Tests use throwaway temp dirs (`mkdtempSync`), never the real home.
- Use LANGUAGE.md's vocabulary (Client, Factory, ProductionLine, Foreman, Worker, task, checks, delivery, verdict, caps) in code and messages — don't invent synonyms. `Fabrica` is the Factory's name (`~/.fabrica`, the `fabrica` command, and the factory's own types `FabricaTask`/`FabricaEvent`/`FabricaEventName`) — it is not a second name for the Foreman. `Foreman` is settled (PR #43) as the name for `src/foreman/`'s delegator module, its interface (`contract/surface.ts`'s `Foreman`), and `createForeman`; do not rename these to "Fabrica" again.
- `contract/surface.ts` declares every shared type (`Brain`, `Delivery`, `Foreman`, `ProductionLine`, etc.) exactly once, imported into `src/` as a type (`import type`, erased at compile time — no runtime dependency), and has no functions at all. `src/index.ts` is the single public entry point implementing those seams — `createForeman`, `ForemanError`, `validateDelivery`, `loadConfig`/`requireProject`/`ConfigError` (config), `defaultBrainAdapter` (brain, issue #47) — and is what every `contract/*.test.ts` imports the implementation from (issue #45's `createForeman`/`createFabrica` precedent, issue #9's `validateDelivery` repoint followed it exactly), and what `src/cli/` imports from too, never an internal module path directly. Adding a new src-internal capability the CLI needs means exporting it here, not reaching into `src/config`/`src/brain`/etc. from `src/cli/`.
- `src/delivery/`'s `validateDelivery(value)` (issue #9, CONTRACT rule 4) checks a `Delivery` object structurally, nothing more. It used to also diff `delivery.branch` and reject a `files` list that disagreed (`validateDeliveryFiles`); Client ruling removed it (issue #9 follow-up) and **it must not come back** — `do.ts` builds `files` *from* that same diff, so comparing them compares a value to itself and can never fail. See `src/delivery/README.md`'s "Why there's no check against the branch's real diff" for the full reasoning.
- CONTRACT rule 9 enforcement went through two designs that were tried and replaced by Client ruling (PR #54 follow-ups) — **do not re-introduce either**: force-resetting the branch and saving a `discarded.patch` (`discard.ts` and that record file are gone), then renaming the branch to `fabrica/discarded/<taskId>` for CI to key on. Both put the enforcement signal inside Fabrica's own output, where a detection bug or an evading Worker could leave it unwritten. Today `do.ts` commits a Worker's changes onto the ordinary `fabrica/<taskId>` branch unconditionally for every outcome (`commit.ts`, which already no-ops when nothing is staged — `src/foreman/files.ts`'s `listTouchedFiles` was deleted rather than kept as a redundant pre-check), and enforcement lives entirely outside Fabrica in `.github/workflows/rule9-gate.yml`: it queries the GitHub API for the pull request's changed-file list against protected paths (`check.sh`, plus `.github/workflows/**` so the gate protects its own definition). It runs on `pull_request_target`, not `pull_request` — **do not switch it back** — so a PR can't rewrite the gate checking it; the job must never check out or execute anything from the branch, only compare filenames the API supplies, and the job name `block-protected-path-change` must not change (it's wired into required-status-check settings). See `src/foreman/README.md`'s "Rule 9: blocked by CI, not by Fabrica's own mark" for the full reasoning. Issue #53 (Client ruling 2026-08-05) added a second, separately-worded matching pass in that same job and file (`CONTRACT_PROTECTED_PATHS` / `contract/**` + `CONTRACT.md`) — deliberately not folded into rule 9's `PROTECTED_PATHS` or its message, because touching the contract is not itself a violation the way touching `check.sh` is; it just may never merge itself. `contract/rule9-gate.contract-paths.test.ts` proves that pattern list and wording exist by reading the workflow file directly, since there is no Fabrica code involved to unit-test. **A PR that edits the workflow, or touches `contract/`/`CONTRACT.md`, therefore fails `block-protected-path-change` itself, on purpose** — GitHub runs the base branch's copy of the workflow, so no commit on the branch can turn that check green, and the only way to get a green tick is to drop the protected-path change. Never do that to satisfy CI; the Client merges these by hand.
- `src/line/helpers/fixture.ts` and three `src/foreman/*.test.ts` files import `makeFixtureRepo`/`fingerprint` from `contract/helpers/` on purpose (issue #45 decision, kept deliberately): both suites measuring the "untouched checkout" proof with the same `fingerprint()` ruler is a feature, and these are test-only imports, not production code depending on the contract. - `src/record/` (issue #3) is the append-only event log (`events.jsonl`) plus per-task folders; its structural append-only proof spawns real `tsx` child processes (see `src/record/helpers/concurrent-append-worker.ts`) rather than interleaving async calls in one process, since only genuine OS-level concurrency can prove a write can't be torn. Reuse that pattern for any other append-only file (e.g. `transcript.log`).
- On macOS, `os.tmpdir()` resolves through a `/var` -> `/private/var` symlink. Any code or test that computes a path under a temp dir and later compares it against a `realpathSync`'d value (as `src/line` does for its worktree paths) must compare against the realpath'd form on both sides, or the comparison spuriously fails.
- `src/line/` (`ProductionLine`, declared once in `contract/surface.ts` as CONTRACT rule 1's central shape and imported here as a type — issue #45: creating/destroying the throwaway git worktree per task) is the reference example for path-safety code: never delete or write to a path without first proving via `git worktree list` that it's the exact throwaway path expected, not a live checkout. `destroyProductionLine` returns a `TeardownResult` (`{ status: "destroyed" | "already-destroyed" }`), not `void` — a second teardown of the same line is idempotent success, not a thrown `unsafe-teardown`; only a workdir that never was this line's still throws.

- A CLI adapter's fast-test fake (e.g. `adapters/helpers/fake-claude-cli.mjs`) can silently drift from what the real binary emits (issue #46) - `adapters/README.md`'s "Guarding a fake against drift from the real thing" is the settled, copy-for-the-next-adapter pattern: a loud (not silent) skip on whatever test drives the real binary (`claude-code.test.ts`'s `after()` banner), plus a fixture-parity test (`adapters/helpers/fake-claude-cli.test.ts`) that always runs, comparing the fake's output *shape* against a real sample recorded once (`adapters/helpers/fixtures/`, re-recorded by hand via `record-real-cli-fixture.mjs` - see that directory's README for what "shape" deliberately does and doesn't cover). Running the real binary in CI itself was deliberately left unbuilt - that needs an authenticated install and real CI spend, a decision for whoever configures Fabrica's CI, not an adapter's own tests.
- `src/foreman/` (issue #7) is `createForeman`'s real implementation: registers a task, cuts a ProductionLine, runs the counted attempt loop, verifies with the project's check, delivers, tears down. `Delivery` and `Receipt[]` are stored on the `"delivered"` event's `details` (there's no dedicated record file for them) — `deliveryOf`/`receiptsOf` read that back, never parse `delivery.md`. See `src/foreman/README.md` for why `attempts` behaves differently when given explicitly vs. omitted, and why the check command defaults to a `check.sh` convention.
- `src/cli/` (issue #47) is the installed `fabrica` command (`package.json`'s `bin` → `src/cli/bin.mjs`), built entirely on top of `src/index.ts`. Sharp edge worth knowing before touching any bin-like script here: `node --import <bare-specifier>` resolves that specifier against the process's *current working directory*, not the script's own location — breaks the instant the command runs from outside this repo. `bin.mjs`/`tsx-bootstrap.mjs` sidestep it with a real `import "tsx/esm"` (resolved via `import.meta.url`, i.e. against the file itself) instead of the CLI flag; verified against the real runtime, not assumed. Its sibling, which has already bitten twice: `import()` parses its argument as a *URL*, so a runtime-computed filesystem path must go through `pathToFileURL(p).href` first — a checkout path containing `#` or `?` (this fleet's generated worktree paths can) otherwise truncates there — see `src/cli/README.md`'s "Why nothing here ever `import()`s a raw filesystem path". That fix closes `#` completely but only half-closes `?`: tsx's own TypeScript transform has a separate, unfixable-from-here bug that still breaks on `?` for real TypeScript syntax regardless of `pathToFileURL` — `bin.mjs` and `tsx-bootstrap.mjs` therefore refuse outright at startup on a `?` in the relevant resolved path rather than attempting it, with a plain explanation instead of tsx's own confusing transform error — see `src/cli/README.md`'s "Why a checkout path can never contain a literal `?`" for the observed error and full reasoning, kept in enough detail to file upstream. `fabrica do` runs the loop in a detached, `setsid`'d child process and learns its task id by watching `recordHome/tasks/` from the outside rather than changing `doTask` — see `src/cli/README.md` for the full mechanism and its one documented race (identical task text, same record home, same narrow window).
- `fabrica answer` (issue #8, SPEC.md step 2 "Clarify-or-proceed") gave `Brain` a second, narrower method, `ask(brief)` — no `workdir` parameter, so CONTRACT rule 1 holds by construction for this call, not by trusting a brain's good behavior. `src/foreman/ask.ts`'s `registerAndAsk` runs it right after registering, before any ProductionLine is cut; a non-empty `questions` result appends `"questions-asked"` (details carry `project`/`totalAttempts`/`explicitAttempts`, since no ProductionLine exists yet to remember them on) and `doTask` returns `{ state: "asking" }` immediately — `src/foreman/do.ts`'s isolate/work/verify/deliver body is factored out as the exported `runProductionRound`, shared with `src/foreman/answer.ts`'s `answerTask` (what `contract/surface.ts`'s `Foreman.answer` — no `brain` parameter, same per-instance brain memory as `verdict()` — calls to resume). Resuming never calls `ask()` again: v1's ask-first dial is fixed at "ask," not a negotiable loop, so `answerTask` refuses a second `fabrica answer` on the same task with `ForemanError("already-answered")` — but only once that round actually delivered; a round that threw first (missing check command, moved project, unreachable brain) stays retryable — that means the task stays resumable and reports its real error each time, not that a retry succeeds (a failure baked into the already-cut branch throws identically forever; see `src/foreman/README.md`). `runProductionRound` takes an explicit `isRetry` the caller derives from the record (`answerTask`: this exact taskId already has a `"line-cut"` event, which `runProductionRound` appends the moment the line genuinely exists) to choose `reopenProductionLine` over `createProductionLine` — deliberately **not** from `"answers-given"`, which `answerTask` writes *before* the line is cut, so a resume that dies on the cut itself (moved project, stale `.git/index.lock`) would otherwise be a "retry" forever and die on `no-such-branch` (Client ruling, PR #69 review; moving the `"answers-given"` append later was considered and rejected — a second answer would duplicate a round in `answers.md`) — and deliberately **not** decided from whether a `fabrica/<taskId>` branch happens to exist in the project (`src/line/resume.ts`'s `productionLineBranchExists` is still there, but module-private now, only for `reopenProductionLine`'s own internal check): a taskId is unique only within one record home, so a same-named branch left by a different record home or a hand-made one could otherwise get silently adopted and committed onto on a task's actual first round, exactly where `createProductionLine`'s loud refusal belongs (Client ruling, issue #8 follow-up — do not revert to deciding this from git state). The reference adapter's `ask()` (`src/brain/adapters/claude-code.ts`) runs in a fresh, empty scratch dir (no git mounts, no ProductionLine involved) rather than reusing `work()`'s containment setup — see `claude-code.md`'s "`ask(brief)`" section for the prompt shape and why a session never carries across the `ask()`/`work()` boundary. `src/cli/do-command.ts` does a bounded poll (`wait-for-ask-outcome.ts`, default 60s) after spawning the detached task, watching for `"questions-asked"` vs `"work-started"` vs `"ask-failed"`, so `fabrica do` can stop and explain itself when a task asks, or exit non-zero with the real reason when `brain.ask()` itself throws (the reference adapter's documented credential gap is today's live path) — `ask.ts`'s `registerAndAsk` records `"ask-failed"` (details: `{ error }`) before rethrowing, so a task's own record always says what happened even though nothing beyond `"task-received"` otherwise would (Client ruling, issue #8 follow-up: "a failed task must never look like a started one"; `queries.ts`'s `stateOf` reports it as `"failed"` too). A genuinely slow (not failed) brain still just falls back to nothing further to report on timeout — that distinction is deliberate, not an oversight: a real timeout for "still thinking," a direct signal for "threw." Stdout stays exactly the task id, one line, in every case, even the asking and failed ones (Client ruling, issue #8 follow-up) — `id=$(fabrica do ...) || exit 1` (`src/cli/README.md`) must keep working verbatim; the numbered questions/`fabrica answer` hint and the failure reason print to stderr instead, and there is deliberately no separate exit code for the asking case, but the failed case does exit 1 (the one case this contract must actually distinguish, since a script's `||` depends on it).
- `src/containment/` (issue #44) runs a command inside a fresh, throwaway Docker container — bind-mounted to `workdir` (writable) and nowhere else by default, network denied unless deliberately allowed, resource caps (`--memory`/`--cpus`/`--pids-limit`) always applied and verified enforced (not just documented), the Docker socket never mounted. Docker only, no OS-specific fallback (an earlier macOS `sandbox-exec` version was fully replaced — its own `man` page opens with "DEPRECATED", and it couldn't reach the reference adapter's Keychain-based credential anyway). `src/brain/adapters/claude-code.ts` always runs through it (`runContained`, no toggle, no uncontained path) via a project-owned, digest-pinned image (`src/brain/adapters/docker/Dockerfile`, built once as `fabrica-claude-code:latest`) — that image's own Linux build of the CLI genuinely executes, but has no credential configured yet. Two more gaps containment first exposed are now closed: git (`src/line/worktree-git.ts`'s `resolveCommonGitDir` mounts the real project's shared `.git` back in read-only, so `git status`/`log`/`diff` work but `git commit` fails on a read-only filesystem — deliberately, since Workers must never commit their own work; the one credential-bearing file in it, `config`, is never the real one — `writeSanitizedGitConfig` shadow-mounts a copy forwarding only the `[core]` section plus an explicit allowlist of credential-free `[extensions]` keys (an allowlist, not a denylist; an off-allowlist extension key fails the run with `LineError("unsanitizable-config")`, never silently dropped or forwarded — see `src/containment/README.md` for the key list and the known `partialClone` limitation) so no remote URL, embedded credential, credential helper, or any other config-borne credential mechanism is readable inside the container; there is no no-git fallback — a workdir whose git mounts can't be resolved refuses the run with an instructive error, so adapter test fixtures must be real ProductionLine worktrees) and warm sessions (`runContained`'s `homeDir` persists a per-`workdir` `$HOME` across calls, since every call is otherwise a fresh throwaway container). See `src/containment/README.md` and `claude-code.md` ("Process containment") for the exact, current status and what's still open (the credential gap, and that nothing yet deletes a task's session directory on teardown).

- `fabrica status`/`log`/`watch` (issue #12) are the Client's eyes and live in `src/cli/status-command.ts`/`log-command.ts`/`watch-command.ts`, sharing render helpers (`src/cli/render.ts`: `formatAge`, `formatStatusLine`, `isQuietTooLong`, `QUIET_THRESHOLD_MS`) so age/quiet/verdict wording reads identically everywhere. A "heartbeat" event (already in `contract/surface.ts`'s `FabricaEventName` union from the start) now actually fires: `src/foreman/attempts.ts`'s `runAttempts` wraps each `brain.work()` call in a `setInterval` (`onHeartbeat`, `DEFAULT_HEARTBEAT_INTERVAL_MS` = 15s) since that call is one long opaque await with nothing else to report mid-flight — both `do.ts` and `verdict.ts`'s fix round wire it to `appendEvent(..., "heartbeat")`. The project a task runs against rides on `work-started`'s event `details.project` (not a dedicated event) — `src/cli/render.ts`'s `projectFromEvents` is the one reader of it and takes "whichever event last carried it," since a fix round's `work-started` and every `delivered` event carry it too; it works off events the caller already fetched, so don't add a foreman-level equivalent that re-reads `events.jsonl`. `fabrica watch`'s whole reason to exist safely is that it only ever reads the record (`transcript.log` and `events.jsonl`, both via one `src/foreman/follow.ts` `followTask` follower held for the whole run) — it never touches the detached process `fabrica do` spawned, so Ctrl-C there can only stop the polling loop, never the worker; don't add anything to that command that reaches toward process management. A poll must never re-read a whole file: `readTranscript`/`foreman.events` are for one-shot readers (`fabrica log`), while `followTask` reads through `src/record/tail.ts`'s `createLineTail` (a byte offset per file, withholding a line caught mid-append until its newline lands) so each line is parsed exactly once however long the watch lasts — `events.jsonl` holds every task a record home has ever seen and gains a heartbeat per running task every 15s, so a 2Hz full re-read gets expensive fast. `read()` still returns the task's full history each call, because `stateOf` and the quiet/terminal notices all derive from the whole event list. Reuse `createLineTail` for any other followed append-only file rather than tracking an offset by hand. Per this file's CLI-layering rule, `src/cli/` reaches the record only through `src/index.ts`'s re-exports (`readTranscript`, `followTask`, `eventsByTask`, `stateOf`, `DEFAULT_HEARTBEAT_INTERVAL_MS`) and `foreman.events`, never `src/record` directly — tests are exempt and do reach into `src/record` for setup. A task running its check is exempt from the "quiet" alarm below a long ceiling (Client ruling on issue #12): "check-run" now lands twice per attempt — `attempts.ts`'s `onCheckStarted` fires one with `details: {attempt, phase: "started"}` right before the (synchronous, blocking) check runs, and the existing result-carrying one lands once it finishes — deliberately reusing the existing `check-run` name rather than adding a new `FabricaEventName` member, since `contract/surface.ts` is a path `rule9-gate.yml`'s CI check protects (see this file's rule 9 entry); the Client's actual ruling only required real elapsed time to be shown, not a contract change to get it. `src/foreman/queries.ts`'s `stateOf` is a single forward pass over a task's events (not several `.filter().at(-1)` reads) so a `check-run` "started" with no "finished" one after it correctly yields `"checking"`. `src/cli/render.ts`'s `checkStartedAt(events)` finds that in-flight start; `isQuietTooLong` returns false for `"checking"` until the check has been running longer than `CHECKING_QUIET_CEILING_MS` (4 hours, a deliberately different order of magnitude from `QUIET_THRESHOLD_MS` - do not tidy it down to match), so `status`/`watch` show "checking, Xm so far" below it and the ordinary quiet alarm takes over the line past it (Client ruling on a later issue #12 review finding: a worker killed mid-check, or a check hung inside `runCheck`'s blocking `execSync`, otherwise leaves the record on `"check-run"`/`phase: "started"` forever with no alarm ever firing; explicitly a time ceiling, not process-liveness detection, which is a separate issue). Because `runCheck` is synchronous `execSync`, it blocks its own process's event loop for the check's whole duration — a test proving "checking" is observable while a check runs needs a real second OS process (see `status-command.test.ts`/`watch-command.test.ts`'s `sleep N && exit 0` fixture checks driven via `runDoCommand` + `entryScript`), not an unawaited in-process promise, which never gets a turn to run until the blocking call returns.

Sharp edge rule 8's brain-word scan (`contract/rule8.no-favorite-brain.test.ts`) creates: it flags a harness's name as plain text anywhere under `src/`, and that includes an **import specifier**, not just comments — `src/cli/verify-hook-command.ts` can't `import` a hardcoded `skill/claude-code/...` path for exactly this reason, so it discovers a `skill/<harness>/verify.ts` by scanning `skill/` at runtime instead. `skill/claude-code/settings.json`'s Bash allowlist deliberately excludes `find` (removed, not narrowed, by Client ruling — that README's own section says why, including why the read-only entries it names (`grep`/`rg`/`cat`/`head`/`tail`/`wc`/`ls`) stay, and why deny patterns aimed at writing through one of them via shell redirection were considered and rejected as a false guarantee) — do not re-add `find`, and do not try to pattern-match redirection shut. Issue #13 also specified a detection half (`checkForOffBooksChanges`, comparing each registered project's git state on every `fabrica` command and logging an `unattributed-change` event — still ratified in `contract/surface.ts`, emitted by nothing now): built, tested, then cut by Client ruling (issue #13 follow-up, PR #71) — roughly 750 of about 1000 lines, 468 of them tests, mostly duplicating what `git status` already shows the Client, for a case the delivery's own `files` list, the inspector, and CI already catch downstream. **It must not come back** without a fresh ruling.

- `skill/claude-code/settings.json`'s Bash allow list (issue #76) names the free commands explicitly - `do`, `status`, `log`, `watch`, `deny-and-log-edit`, `verify-hook` - instead of a broad `Bash(fabrica *)` or a pattern that excludes the deciding ones; `verdict` and `answer` are additionally listed in `permissions.deny`, not just left off the allow list, since deny is checked before allow and wins even if a later edit reintroduces a broader allow entry. Two layers prove this, on purpose not just one: `src/cli/skill-settings.test.ts` derives the real command set from `main.ts`'s dispatch (not a name copied by hand) against a hardcoded `DECIDING_COMMANDS` list, so a command added to `main.ts` without a matching decision in both places fails loudly, and replicates Claude Code's documented Bash-pattern rules (word-boundary prefix matching; shell operators splitting a command into independently-checked subcommands) - but that is still a hand-written model of the rules, not proof the real engine behaves that way. `src/cli/skill-settings-live.test.ts` + `skill/claude-code/permission-boundary-verify.ts` are the empirical layer: a real, non-interactive session of the harness is told to attempt `fabrica status`/`do`/`log`/`watch`, `fabrica verdict`/`answer`, and a chained `fabrica status && fabrica verdict ...`, and the test reads the session's own `permission_denials` field and a marker a fake `fabrica` shim writes - not the model's prose - to confirm the free ones actually ran and the deciding ones, including the whole chained attempt, actually didn't. What that empirical run also surfaced, undocumented anywhere before: a real non-interactive session ignores `permissions.allow` entirely - denying everything, free commands included - unless its working directory is a trusted workspace, and there is no non-interactive flag to grant that without also bypassing every permission check; `permission-boundary-verify.ts` patches the one field the CLI's own warning names (`~/.claude.json`'s `projects[path].hasTrustDialogAccepted`) for the duration of the check and removes exactly that entry after, which is why this test is opt-in (`FABRICA_TEST_REAL_PERMISSIONS=1`) rather than part of the default `npm test` run - see that file's header for why, matching `src/brain/adapters/claude-code.test.ts`'s precedent for real-binary tests that skip loudly rather than lie. **Named limit, not claimed as covered:** both layers model shell-operator chaining (`&&`, `;`, `|`) and word-boundary prefix matching only; neither attempts a command-substitution-style bypass (e.g. `cat $(fabrica verdict ...)`, where the outer command's own prefix is on the allow list) - that remains untested and open, not verified either way.
- **Whether Fabrica itself should enforce the verdict/answer boundary, investigated and not built (issue #76):** a settings template is only as strong as its install and its workspace's trust state (see above) - missing, stale, never applied, or simply untrusted, the guarantee is gone and nothing on Fabrica's side would know. But Fabrica is a CLI binary with no protocol-level signal for "a human typed this" versus "an agent's tool loop generated this" - `settings.json`'s own permission engine has no such concept either, confirmed against Claude Code's documented behavior rather than assumed. One partial, Fabrica-side mechanism was considered: refuse `fabrica verdict`/`fabrica answer` when stdin isn't a real interactive terminal, since both already take all their input as CLI args (no stdin prompt exists to hang the check on) and an agent's Bash tool call is not normally given a real TTY. It was not built, for three reasons that all pointed the same way: it would also block the Client's own legitimate non-interactive use (a script or alias calling `fabrica verdict $id accept`); it is defeatable by a determined agent that allocates its own pty (`script`, `expect`, Python's `pty`), so it is not adversarially robust, only a speed bump against casual/incidental use; and - the reason it needed a ruling rather than a quiet addition - it is exactly "Fabrica enforcing this" instead of "a settings file the Client installs," the re-architecture question issue #76 said needed a decision before building, not a side effect of narrowing an allow list. Weighed and rejected, not built - no escalation needed, since the conclusion was to keep the architecture as-is rather than change it.
