# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

**Index — the rulings that matter most, before anything else below** (grep for the quoted text to jump straight there): `CONTRACT.md`/`contract/` is immutable except by explicit ruling ("the ratified answer key"); Rule 9 is enforced by CI, not Fabrica, and its two replaced designs must not come back ("CONTRACT rule 9 enforcement went through two designs"); the verdict/answer boundary is a settings template the Client installs, not something Fabrica itself enforces (issue #76: "Bash allow list" and "Whether Fabrica itself should enforce"); and a Worker's write-up is structured data Fabrica renders, never prose Fabrica parses ("Pull requests must read like a human wrote them").

- CONTRACT rule 9 enforcement went through three designs that were tried and replaced by Client ruling — **do not re-introduce any of them**: force-resetting the branch and saving a `discarded.patch` (`discard.ts` and that record file are gone), then renaming the branch to `fabrica/discarded/<taskId>` for CI to key on (PR #54 follow-ups), then (the one that survived longest) `src/foreman/gate-changes.ts`'s own host-side `git diff` of `check.sh` against the task's pinned `baseCommit`, forcing a dedicated `discarded-protected-path` outcome on an undeclared change. The first two put the enforcement signal inside Fabrica's own output, where a detection bug or an evading Worker could leave it unwritten; the third kept enforcement outside but still ran a host-side watch over a file the Worker just edited. The October 8 2026 ruling on issue #64 ("Fabrica runs no project check on the host") removed that third design too (issue #190): `gate-changes.ts`, `requireGateBaseline`, `gateWasTouched`, and the `discarded-protected-path` outcome are gone from `Receipt`/`Delivery["outcome"]` entirely. Fabrica now detects nothing about rule 9 — the only trace left on its side is `gateChanges`, the Worker's own declared intent, carried onto the delivery (`round.ts`'s `mergeGateDeclarations`) and never verified against anything. `do.ts` commits a Worker's changes onto the ordinary `fabrica/<taskId>` branch unconditionally for every outcome (`commit.ts`, which already no-ops when nothing is staged — `src/foreman/files.ts`'s `listTouchedFiles` was deleted rather than kept as a redundant pre-check), and detection plus enforcement live entirely outside Fabrica in `.github/workflows/rule9-gate.yml`: it queries the GitHub API for the pull request's changed-file list against protected paths (`check.sh`, plus `.github/workflows/**` so the gate protects its own definition). It runs on `pull_request_target`, not `pull_request` — **do not switch it back** — so a PR can't rewrite the gate checking it; the job must never check out or execute anything from the branch, only compare filenames the API supplies, and the job name `block-protected-path-change` must not change (it's wired into required-status-check settings). See `src/foreman/README.md`'s "Rule 9: blocked by CI, not by Fabrica, and not watched by Fabrica either" for the full reasoning. Issue #53 (Client ruling 2026-08-05) added a second, separately-worded matching pass in that same job and file (`CONTRACT_PROTECTED_PATHS` / `contract/**` + `CONTRACT.md`) — deliberately not folded into rule 9's `PROTECTED_PATHS` or its message, because touching the contract is not itself a violation the way touching `check.sh` is; it just may never merge itself. `contract/rule9-gate.contract-paths.test.ts` proves that pattern list and wording exist by reading the workflow file directly, since there is no Fabrica code involved to unit-test. **A PR that edits the workflow, or touches `contract/`/`CONTRACT.md`, therefore fails `block-protected-path-change` itself, on purpose** — GitHub runs the base branch's copy of the workflow, so no commit on the branch can turn that check green, and the only way to get a green tick is to drop the protected-path change. Never do that to satisfy CI; the Client merges these by hand. Issue #96 adds a third, temporary pass after the contract pass: `TEST_PROTECTED_PATHS` / `*.test.ts`. Contract tests retain the contract message; other test changes require the Client's direct review until Inspector's examiner (inactdev/inspector#7) lands, then this pass must be removed. This is CI enforcement only, unrelated to `gateChanges`. CONTRACT.md's rule 9 text still describes the pre-issue-#190 shape (it says Fabrica "knows the gate's before-state" and records "any undeclared change to it") — that wording is now wrong about the implementation and is the Client's to fix; proposed replacement wording was handed over in issue #190's write-up, not applied here.

- `src/record/` (issue #3) is the append-only event log (`events.jsonl`) plus per-task folders; its structural append-only proof spawns real `tsx` child processes (see `src/record/helpers/concurrent-append-worker.ts`) rather than interleaving async calls in one process, since only genuine OS-level concurrency can prove a write can't be torn. - On macOS, `os.tmpdir()` resolves through a `/var` -> `/private/var` symlink. Any code or test that computes a path under a temp dir and later compares it against a `realpathSync`'d value (as `src/line` does for its worktree paths) must compare against the realpath'd form on both sides, or the comparison spuriously fails.
- `src/line/` (`ProductionLine`, declared once in `contract/surface.ts` as CONTRACT rule 1's central shape and imported here as a type — issue #45: creating/destroying the throwaway git worktree per task) is the reference example for path-safety code: never delete or write to a path without first proving via `git worktree list` that it's the exact throwaway path expected, not a live checkout. `destroyProductionLine` returns a `TeardownResult` (`{ status: "destroyed" | "already-destroyed" }`), not `void` — a second teardown of the same line is idempotent success, not a thrown `unsafe-teardown`; only a workdir that never was this line's still throws. A new task's branch is cut from `origin`'s default branch, never the project's local checkout (`cut.ts`'s `fetchOriginBase`: `git fetch origin` then `git ls-remote --symref origin HEAD` to read which branch is default, straight from the remote, never assumed to be "master"); either step failing throws `LineError("fetch-failed")` before the task's working folder is created at all, never falling back to local HEAD. The worktree is cut with `--no-track` (a throwaway task branch has no business tracking origin's default branch, and skipping it avoids a `.git/config` write two concurrent creates from the same project could collide over). `reopenProductionLine` is unaffected — a fix round resumes the branch exactly where its own history left it, no fetch involved. Because of this, `contract/helpers/fixture.ts`'s `makeFixtureRepo` now points every fixture project's `origin` at a throwaway bare mirror by default (`addOrigin`, with its `HEAD` symref set correctly — a bare repo's own default is "master" regardless of what's actually pushed); `{ origin: false }` opts out for the handful of tests that deliberately want no origin configured, and `pushToOrigin(dir)` is for a test that commits into a fixture project after creation and needs that commit visible to a later `createProductionLine` call.

- CONTRACT rule 10 (issue #11) is `src/foreman/spend.ts` (the ledger) plus `caps.ts` (enforcement); `src/foreman/README.md`'s "Rule 10: spending caps" owns the semantics. Sharp edges: spend is always derived from the record, never held in memory; "daily" is a rolling 24 hours from receipt `startedAt`, not a calendar day; an unknown cost (`costUsd: null`, marked `costUnknown: true`) is never counted as zero, and while any cap is set it blocks every new start until `fabrica cost <id> <usd>` records the real figure. Issue #188 (the August 2026 ruling on #6) split every dollar figure by `Receipt.costBasis`: `"metered"` (real, billed money - the default when a usage entry says nothing) or `"subscription-estimate"` (a flat-rate subscription's own notional figure, which the reference adapter now always marks, having been fixed from the opposite default). `spend.ts`'s `daySpend`/`taskSpend` return `SpendTotals` (`{ meteredUsd, subscriptionUsd }`) instead of one `knownUsd`; `requireRoomToStart`/`spendLimitsFor` bind only on `meteredUsd`, so a subscription estimate - however large - never refuses or stops a task on its own. `fabrica status` and the live view still show it, separately, marked with a "~". - `src/foreman/` is `createForeman`'s implementation: it runs the counted loop, hands configured green work to Inspector, records a delivery or refusal, and tears down the ProductionLine. `src/foreman/README.md` owns the event and query semantics, attempt behavior, and default check convention.
- `src/cli/` (issue #47) is the installed `fabrica` command (`package.json`'s `bin` → `src/cli/bin.mjs`), built entirely on top of `src/index.ts`. Sharp edge worth knowing before touching any bin-like script here: `node --import <bare-specifier>` resolves that specifier against the process's *current working directory*, not the script's own location — breaks the instant the command runs from outside this repo. `bin.mjs`/`tsx-bootstrap.mjs` sidestep it with a real `import "tsx/esm"` (resolved via `import.meta.url`, i.e. against the file itself) instead of the CLI flag; verified against the real runtime, not assumed. Its sibling, which has already bitten twice: `import()` parses its argument as a *URL*, so a runtime-computed filesystem path must go through `pathToFileURL(p).href` first — a checkout path containing `#` or `?` (this fleet's generated worktree paths can) otherwise truncates there — see `src/cli/README.md`'s "Why nothing here ever `import()`s a raw filesystem path". That fix closes `#` completely but only half-closes `?`: tsx's own TypeScript transform has a separate, unfixable-from-here bug that still breaks on `?` for real TypeScript syntax regardless of `pathToFileURL` — `bin.mjs` and `tsx-bootstrap.mjs` therefore refuse outright at startup on a `?` in the relevant resolved path rather than attempting it, with a plain explanation instead of tsx's own confusing transform error — see `src/cli/README.md`'s "Why a checkout path can never contain a literal `?`" for the observed error and full reasoning, kept in enough detail to file upstream. `fabrica do` runs the loop in a detached, `setsid`'d child process and learns its task id by watching `recordHome/tasks/` from the outside rather than changing `doTask` — see `src/cli/README.md` for the full mechanism and its one documented race (identical task text, same record home, same narrow window).
- `fabrica answer` (issue #8, SPEC.md step 2 "Clarify-or-proceed") gave `Brain` a second, narrower method, `ask(brief)` — no `workdir` parameter, so CONTRACT rule 1 holds by construction for this call, not by trusting a brain's good behavior. `src/foreman/ask.ts`'s `registerAndAsk` runs it right after registering, before any ProductionLine is cut; a non-empty `questions` result appends `"questions-asked"` (details carry `project`/`totalAttempts`/`explicitAttempts`, since no ProductionLine exists yet to remember them on) and `doTask` returns `{ state: "asking" }` immediately — `src/foreman/do.ts`'s isolate/work/verify/inspect/result body is factored out as the exported `runProductionRound`, shared with `src/foreman/answer.ts`'s `answerTask` (what `contract/surface.ts`'s `Foreman.answer` — no `brain` parameter, same per-instance brain memory as `verdict()` — calls to resume). Resuming never calls `ask()` again: v1's ask-first dial is fixed at "ask," not a negotiable loop, so `answerTask` refuses a second `fabrica answer` on the same task with `ForemanError("already-answered")` - but only once that round completed with a delivery or Inspector refusal; a round that threw first (missing check command, moved project, unreachable brain) stays retryable — that means the task stays resumable and reports its real error each time, not that a retry succeeds (a failure baked into the already-cut branch throws identically forever; see `src/foreman/README.md`). `runProductionRound` takes an explicit `isRetry` the caller derives from the record (`answerTask`: this exact taskId already has a `"line-cut"` event, which `runProductionRound` appends the moment the line genuinely exists) to choose `reopenProductionLine` over `createProductionLine` — deliberately **not** from `"answers-given"`, which `answerTask` writes *before* the line is cut, so a resume that dies on the cut itself (moved project, stale `.git/index.lock`) would otherwise be a "retry" forever and die on `no-such-branch` (Client ruling, PR #69 review; moving the `"answers-given"` append later was considered and rejected — a second answer would duplicate a round in `answers.md`) — and deliberately **not** decided from whether a `fabrica/<taskId>` branch happens to exist in the project (`src/line/resume.ts`'s `productionLineBranchExists` is still there, but module-private now, only for `reopenProductionLine`'s own internal check): a taskId is unique only within one record home, so a same-named branch left by a different record home or a hand-made one could otherwise get silently adopted and committed onto on a task's actual first round, exactly where `createProductionLine`'s loud refusal belongs (Client ruling, issue #8 follow-up — do not revert to deciding this from git state). The reference adapter's `ask()` (`src/brain/adapters/claude-code.ts`) runs in a fresh, empty scratch dir (no git mounts, no ProductionLine involved) rather than reusing `work()`'s containment setup — see `claude-code.md`'s "`ask(brief)`" section for the prompt shape and why a session never carries across the `ask()`/`work()` boundary. `src/cli/do-command.ts` waits after spawning the detached task (`wait-for-ask-outcome.ts`, no fixed cutoff since #73 - it prints "still waiting on the clarifying step" every 15s, and treats the task's process ending with nothing recorded as a failure) for `"questions-asked"`, `"cap-refused"`, `"ask-failed"`, `"task-failed"` or `"work-started"`, so `fabrica do` can stop and explain itself when a task asks, or exit non-zero with the real reason when `brain.ask()` itself throws (the reference adapter's documented credential gap is today's live path) — `ask.ts`'s `registerAndAsk` records `"ask-failed"` (details: `{ error }`) before rethrowing, so a task's own record always says what happened even though nothing beyond `"task-received"` otherwise would (Client ruling, issue #8 follow-up: "a failed task must never look like a started one"; `queries.ts`'s `stateOf` reports it as `"failed"` too). Any error after `task-received` and before a delivery or refusal appends `"task-failed"` (details: `{ message }`, `src/foreman/task-failure.ts`; a failure already named by `ask-failed`/`cap-refused` is not recorded twice), so a task that died never reads as working; `fabrica do` prints its message and exits 1. Stdout stays exactly the task id, one line, in every case, even the asking and failed ones (Client ruling, issue #8 follow-up) — `id=$(fabrica do ...) || exit 1` (`src/cli/README.md`) must keep working verbatim; the numbered questions/`fabrica answer` hint and the failure reason print to stderr instead, and there is deliberately no separate exit code for the asking case, but the failed case does exit 1 (the one case this contract must actually distinguish, since a script's `||` depends on it).
- `src/containment/` (issue #44) runs a command inside a fresh, throwaway Docker container — bind-mounted to `workdir` (writable) and nowhere else by default, network denied unless deliberately allowed, resource caps (`--memory`/`--cpus`/`--pids-limit`) always applied and verified enforced (not just documented), the Docker socket never mounted. Docker only, no OS-specific fallback (an earlier macOS `sandbox-exec` version was fully replaced — its own `man` page opens with "DEPRECATED", and it couldn't reach the reference adapter's Keychain-based credential anyway). `src/brain/adapters/claude-code.ts` always runs through it (`runContained`, no toggle, no uncontained path) via a project-owned, digest-pinned image (`src/brain/adapters/docker/Dockerfile`, built once as `fabrica-claude-code:latest`) — that image's own Linux build of the CLI genuinely executes, but has no credential configured yet. See `src/containment/README.md` and `claude-code.md` ("Process containment") for the exact, current status and what's still open (the credential gap, and that nothing yet deletes a task's session directory on teardown).
- `src/relay/` (issue #186, first half) is the host-side relay a worker box's traffic is forced through instead of reaching the network itself, plus `src/containment/isolated-network.ts`'s Docker side of that: a `docker network create --internal` network (the worker's container attaches via `runContained`'s new `network: { isolatedNetwork }` form) whose own gateway IP - the one address a container on it can still reach - is where the relay binds. Two traffic shapes, handled differently on purpose: `CONNECT` ("tunnel mode") is allowed or refused by hostname against a short fixed list (`allowlist.ts`'s `GITHUB_HOSTS` plus whatever a caller adds) and then piped untouched, so it can never see or swap anything riding inside it; everything else ("gateway mode") is forwarded to the one upstream a `GatewayTarget` names, with a configured header's value overwritten to the real credential first — this is the "swaps a per-task fake key for the real one" half, done with no TLS termination anywhere, since the worker-to-relay leg is never more than plain HTTP on a network nothing outside the task can observe. - `integrations/herdr/` (rebuilt 2026-10-14) mirrors the record into Herdr using exactly four Herdr commands the Client verified by hand - `tab create`, `pane run`, `pane report-agent`, `pane release-agent` - and no others; it never splits a pane or renames an agent. A task's Herdr tab is opened with `herdr tab create --no-focus --label "<title>"` (pane id parsed from the JSON response's `result.root_pane.pane_id`, never raw stdout), then `pane run` starts `fabrica watch <id>` in it, then `pane report-agent` registers the row - all three keyed off a title (the task text's first line, capped at 60 chars) that is computed once and reused as every later call's `--agent` value, since there is no rename call to give it one separately. `heartbeat`/`delivered`/`questions-asked`/`task-failed` map to `report-agent` calls with state `working`/`idle`/`blocked`/`blocked` respectively (the only three states ever sent); a `verdict-recorded` with ruling `accept`/`wrong` calls `release-agent` instead and stops tracking the task, while `fix` does neither (the next heartbeat already reports `working` again). `--seq` is a per-task counter starting at 1, incrementing by one on every report/release call for that task. Every Herdr call is wrapped (`herdr-watcher.ts`'s `tryHerdr`) so a failure is logged to `<recordHome>/herdr-watcher.log` with its exact args and Herdr's own output, and the watcher keeps running - a failed `tab create` just skips that task (no pane id to do anything else with). `fabrica up`'s hook (`up-hook.ts`) distinguishes "never-started" from "exited" (`herdrWatcherStatus`, by pid-file liveness) and only prints a notice - via the generic `notify` callback now threaded through `src/cli/up-command.ts`'s `UpIntegrationHook.maybeStart(opts)` (an addition to that interface, not Herdr-specific) - when a watcher that really was running has since exited; an ordinary first start stays silent.
